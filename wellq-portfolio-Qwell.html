01 / Context

แต่คือกติกาของระบบ

องค์กรต้องประกาศและตรวจสิทธิใหม่เป็นรอบรายปี แม้ข้อมูลหลักของผู้มีสิทธิส่วนใหญ่จะคงเดิม ส่งผลให้งานเดียวกันเกิดซ้ำทั้งฝั่งผู้ยื่น เจ้าหน้าที่ส่วนกลาง และโรงพยาบาล

01

กรอกข้อมูลเดิมซ้ำ และไม่เห็นสถานะสิทธิของตนเองอย่างชัดเจน

Problem statement — ระบบเดิมสร้างงานตามปฏิทิน — ถึงรอบปี ทุกคนต้องกรอกและตรวจใหม่ทั้งหมด ทั้งที่งานควรเกิดเฉพาะเมื่อ "ข้อมูลเปลี่ยน" ไม่ใช่เมื่อ "ถึงเวลา"

Evidence & scope

ขอบเขตหลักฐานของเคสนี้

“WellQ” เป็นชื่อสมมติ และรายละเอียดบางส่วนถูกปรับเพื่อรักษาความลับของลูกค้า · Discovery รอบนี้ครอบคลุม stakeholder ฝั่งปฏิบัติการทั้งสองหน่วยงาน ส่วนมุมมองผู้มีสิทธิปลายทางจะถูกตรวจสอบใน usability test ตามแผนท้ายเคส

ตัวเลขทุกจุดมาจากบันทึกจริง หรือเป็นผลที่เกิดจากโครงสร้างของ workflow ใหม่โดยตรง (ระบุเงื่อนไขกำกับเสมอ) · เคสนี้แสดงเฉพาะข้อมูลที่จำเป็นต่อการอธิบายกระบวนการออกแบบ และไม่มีข้อมูลส่วนบุคคลของผู้เกี่ยวข้อง

03 / Key insight

จาก time-based
สู่ event-based

เปลี่ยน model ของงาน: บันทึกข้อมูลหลักครั้งแรกและเปิดงานตรวจเฉพาะเมื่อเกิด event ที่มีผลต่อสิทธิ

Before

Annual cycle

1ประกาศรอบใหม่
2กรอกข้อมูลเดิม
3ตรวจทั้งหมดอีกครั้ง
4แจ้งผลและเก็บเอกสาร
→

After

Change events

1ตั้งค่าข้อมูลครั้งแรก
2เห็นสิทธิปัจจุบัน
3เกิด event ที่เกี่ยวข้อง
4ตรวจเฉพาะส่วนที่เปลี่ยน
เปลี่ยนตำแหน่งย้ายที่อยู่เปลี่ยนโรงพยาบาลเปลี่ยนประเภทสิทธิข้อมูลครอบครัวเปลี่ยน
ปีที่ข้อมูลไม่เปลี่ยนฟิลด์ที่ต้องกรอกซ้ำ: ทั้งหมด → 0
คิวตรวจของเจ้าหน้าที่ทุกรายการทุกปี → เฉพาะรายการที่มี event
การเห็นสถานะสิทธิรอรอบประกาศ → ดูได้ตลอดเวลา

นิยามปริมาณงานเปลี่ยนที่ระดับโครงสร้าง: จาก "ต้องตรวจผู้มีสิทธิทั้งหมดทุกรอบปี" เหลือ "เฉพาะผู้สมัครใหม่ + ผู้ที่ข้อมูลเปลี่ยนจริง" — เปอร์เซ็นต์ที่ลดจริงขึ้นกับอัตราการเปลี่ยนของข้อมูลแต่ละปี ซึ่งยังไม่มีข้อมูล production จึงไม่อ้างตัวเลข ตัวชี้วัดจริงอยู่ในแผน validation

05 / Design decisions

ทุกหน้าจอมีเหตุผล
จากงานจริง

ไม่แก้เพียงหน้าตา แต่ลดสิ่งที่ต้องอ่าน ต้องกรอก และต้องตรวจในแต่ละจุดของ workflow

ข้อมูลส่วนใหญ่คงเดิม→แสดงเฉพาะส่วนที่เกี่ยวกับ event→ลดการกรอกซ้ำ
เจ้าหน้าที่ต้องหาสิ่งที่เปลี่ยน→หน้าเทียบก่อน–หลัง (diff) + คิวเฉพาะรายการที่เปลี่ยน→ตรวจได้ตรงจุด
สถานะสิทธิไม่ชัดเจน→หน้ารวมสิทธิ + ไทม์ไลน์การเปลี่ยนแปลง→สร้างความมั่นใจและตรวจสอบย้อนกลับ

07 / Edge cases & trust

ระบบสิทธิต้อง
อธิบายตัวเองได้

ความไว้วางใจไม่ได้มาจากความสวย แต่จากสถานะที่ชัด สิทธิการเข้าถึง และประวัติที่ตรวจสอบย้อนกลับได้

ข้อมูลไม่ตรงกัน

แสดงแหล่งที่มา วันที่อัปเดตล่าสุด และช่องทางส่งหลักฐานเพิ่ม

Event ถูกปฏิเสธ

บอกเหตุผลและ next action โดยไม่ปล่อยให้ผู้ใช้เจอ dead end

สิทธิย้อนหลัง

แยก "วันที่สิทธิมีผล" ออกจาก "วันที่อนุมัติ" และเก็บประวัติทุกการแก้ไข

Privacy & permission

จำกัดการเห็นข้อมูลตามบทบาท พร้อมบันทึก audit log ว่าใครดูหรือแก้ข้อมูลสำคัญเมื่อไหร่

08 / Planned validation

สิ่งที่จะพิสูจน์ต่อ

แผน usability test กับผู้ใช้จริงทั้งสองฝั่ง เพื่อยืนยันว่า workflow ใหม่เข้าใจได้และลดภาระได้ตามที่ออกแบบ

ผู้มีสิทธิดูสิทธิและอัปเดต event

MetricsTask success · time · errors · confidence

Design system · Foundation

ระบบสีและตัวอักษรที่ถอดจากงานจริง

Foundation ของระบบประกอบด้วยสี 4 สเกล สเกลละ 10 ระดับ typeface Prompt สองน้ำหนัก และไอคอนสองขนาด — ค่าทั้งหมดด้านล่างถอดจากเอกสาร design system ของระบบงานจริง ไม่ใช่สีธีมของหน้า portfolio นี้

ขอบเขตหลักฐาน — ค่า font, weight, size และ hex ถอดจากต้นฉบับโดยตรง · ส่วน semantic colors เป็นข้อเสนอเพิ่มที่ติดป้ายกำกับไว้ชัดเจน เพราะต้นฉบับยังไม่ได้กำหนดสีสถานะไว้
